## Почему нужен согласованный переход

Store миграцией `RecordPrices1795300000000` переименовывает
`price_history.offer_uuid` в `record_uuid` и копирует историю оффера каждой его
учётной записи. Cart своей миграцией переносит цену из `store_offer_snapshot`
в `accounting_record_snapshot` и удаляет прежние колонки.

Обе миграции несовместимы со старыми процессами. Общий chart запускает migration
Job в Sync wave `-1`, раньше Deployment. Поэтому обычная автораскатка запустит
миграцию при ещё работающем старом процессе. Нельзя начинать её без остановки
старых Store и Cart.

Этот переход предусматривает окно недоступности API. Время начала согласуется
после успешного CI; продолжительность заранее не обещается.

## Порядок

1. **Удержать автоматическую раскатку.** В Application-манифестах инфраструктуры
   для `dev-store-service`, `dev-cart-service`, `dev-admin-gateway`,
   `dev-client-gateway`, `dev-admin-ui`, `dev-storefront` временно задать
   `syncPolicy.automated.enabled: false`. Сначала опубликовать эту настройку
   отдельно, дождаться её применения родительским Application `sellgar-dev` и
   проверить отсутствие активных sync-операций. Пауза не останавливает поды.
   Правка только live Application без изменения его Git-владельца недостаточна:
   родитель может восстановить автораскатку.

2. **Опубликовать код и получить артефакты.** Push указанных коммитов в
   `development`, затем workspace pointers. Дождаться build, smoke и публикации
   образов и Helm-пакетов всех шести приложений. Зафиксировать версии пакетов,
   source commits, digest новых образов, текущие версии и digest старых образов.
   Все выбранные версии должны быть готовы до начала окна недоступности.

3. **Закрыть доступ на время перехода.** Убедиться, что нет текущих операций
   сохранения. Остановить Admin/Client gateway, затем Cart и Store через их
   Deployment; проверить фактическое завершение старых подов, отсутствие их
   соединений с базами и оставшихся незавершённых команд. Не мигрировать при
   неизвестном активном писателе. PostgreSQL, RabbitMQ, Identity, Product, Shop,
   File, Media и Socket остаются работающими. Локальные watcher и туннели не
   останавливать. Старые браузерные формы нельзя сохранять после открытия доступа
   без обновления клиента.

4. **Сделать резервные копии и контрольные снимки.** После остановки писателей
   снять полные `pg_dump` баз Store и Cart. Сохранить вне Git с ограниченным
   доступом. Проверить завершение dump и возможность восстановления во временные
   базы. Зафиксировать число и UUID учёток, цены и историю офферов, остатки,
   резервы, состав и количество позиций корзин. Не продолжать при ошибке backup.

5. **Обновить Store.** Выполнить ручной sync `dev-store-service` на выбранную
   версию Helm-пакета. Migration Job выполняется без старых писателей; после её
   успеха запускается новый Store. Проверить версию образа, завершение миграции,
   readiness и чтение через внутренний API. Проверить сохранение UUID учёток,
   остатков и резервов; полную историю каждой записи и её соответствие прежней
   истории оффера, включая порядок при одинаковых timestamp. Новые UUID строк
   истории ожидаемы. При ошибке не переходить к следующему этапу.

6. **Обновить Cart.** Старый Cart всё ещё остановлен. Выполнить ручной sync
   `dev-cart-service` на выбранную версию. После миграции запустить Cart с
   `CART_BOOTSTRAP_ON_START=true`, убедившись в фактическом значении настройки.
   Он получает авторитетные снимки из нового Store и сверяет цены даже при
   неизменившейся версии агрегата. Сравнить price UUID, суммы и валюты проекции
   с Store; проверить сохранение количества позиций корзин и пересчёт итогов.
   Одного `/health` недостаточно: он проверяет подключения, а bootstrap
   выполняется асинхронно и при сбое повторяется.

7. **Обновить gateway и UI.** Выполнить ручной sync двух gateway и затем двух UI
   на выбранные версии. Контролировать новые digest и readiness. Admin/Client
   gateway откроют API после запуска; проверки бизнес-данных этапа 6 должны быть
   завершены до этого. Обновить браузерную админку до новой сборки, включая её
   service worker; старые формы цены оффера больше несовместимы с командой Store.

8. **Проверить сквозной сценарий и вернуть автоматику.** На выделенном dev-товаре
   проверить две учётки с разными ценами: изменение одной не меняет другую,
   событие Store обновляет Cart, количество сохраняется, итоги корректны.
   Проверить точную цену рядом с каждой кнопкой на витрине и диапазон в каталоге.
   Вернуть тестовые данные к исходным значениям. Проверить ошибки сервисов,
   отложенные события, DLQ и состояние всех шести Application. Только затем
   отдельным инфраструктурным коммитом убрать временное отключение авто-sync и
   подтвердить, что восстановлены исходные `prune`/`selfHeal` и все Application
   синхронизированы с проверенными версиями. Перед включением проверить, что за
   время окна не опубликована другая непроверенная версия Helm-пакета.

## События

- Очереди RabbitMQ, inbox и outbox не удалять и не очищать.
- Cart использует durable event queue, persistent сообщения и явный ack.
  Остановка consumer сохраняет очередь; после запуска обработка продолжается.
- Новый Cart принимает Store Product schemaVersion `2` и `3`. Новый Admin gateway
  также принимает обе версии. Inventory сохраняет schemaVersion `2`.
- Проверить накопленные события и отсутствие новых ошибок/DLQ после возобновления
  обработки; наличие проблем не маскировать очисткой очереди.
- Миграция Store сама по себе не повышает доменную версию. Поэтому нельзя
  рассчитывать только на новое событие: обязательна сверка авторитетного снимка
  Cart с Store на этапе 6.

## Сбой и восстановление

До миграций можно вернуть прежние Deployment и снять паузу, поскольку схема
ещё не менялась. После миграций простой откат образа запрещён: старые процессы
не понимают новую схему, а `down` явно отклоняется из-за возможной потери разных
цен записей.

При ошибке после изменения схемы удерживать затронутые API закрытыми и прежде
всего рассмотреть исправление новой версии. Восстановление резервных копий
требует отдельного согласованного плана Store/Cart и уже выпущенных событий:
нельзя восстановить только одну базу или удалить сообщения для видимости
успешного отката. Возможность восстановить dump до миграции не доказывает
корректность отката после появления новых данных и событий.

Для последующих изменений схемы с требованием непрерывной доступности нужен
совместимый переход expand/contract отдельными выпусками; текущая реализация
такого перехода не содержит.
